# PDH-Zero rc4：完整对局与随机数据自查

## 审计范围与输入

受众：执行训练的操作者、模型评审者、未来维护者。原包`pdh-zero-v2-trainer-0.6.0-rc4.zip`的SHA256为`21eacdfae3778f05b5cd2d2bfa856cea50163c7fc8244091747cf0764da84545`。真实rc3证据归档SHA256为`0614b811c426fdbd9dca24513676b7082d4496fb7b75ebff3919c07f8a42eba4`。两者已校验，只读审计，没有改写旧实验。

本修订只加强数据协议和审计，不改变原网络、PPO损失、C++特征、房规。此文区分“源码支持什么”“真实日志验证什么”和“还未验证什么”。

## 1. 4096手到底是什么

它是4096次**完整单手对局运行**：1024组不同起始牌墙，每组由候选模型分别控制座位0、1、2、3各打一次，另外三席是启发式对手。每次都从136张牌的自然洗牌发牌开始，按合法动作连续摸打、碰杠、响应，直到胡牌或流局，再抓马和结算。不预先固定后续所有玩家的动作。相同起始牌墙可以因策略不同而走出不同轨迹。

因此不是4096道孤立何切题，也不是4096个互相独立的新牌墙，更不是4096手连续长会话。统计配对的聚类单位是1024个牌墙组。`evaluation_hands`也不是训练数据上限：训练会继续生成其他完整手局。

## 2. 局内历史与跨局边界

采样时每桌每座位有独立GRU状态；每次轮到该座位决策，以其合法可见观察及之前的隐藏状态决定当前动作。PPO保存完整座位Episode，重新按时间顺序计算GRU和行为概率，不把不同局的某一步随机拼接成伪序列。

奖励由完整手局真实净分产生，手局终止后写到末端transition并计算整段优势；因此早期取舍与后续输赢在训练轨迹里相连。实现了这个结构，不等于已经学出正确的长期战略。

训练`GameSession`把庄位、连庄、累计分和因抓马留下的公开信息传给下一局；批次排空后从已发的下一局继续。然而GRU在每手结束时清零，回报不跨手传播。当前受控评估固定起始庄0、连庄0。**不能声称模型已具备跨局记忆、整场收益优化或跨场对手建模能力。** 本修订没有擅自引入新的多局训练目标。

## 3. 真实牌谱核对结果

全量读取rc3的6406手训练记录和5×4096手评估记录，并用“有序牌种序列”计算墙指纹，忽略同种牌四个实体编号互换。

| 数据 | 完整手局条数 | 不同起始牌墙 | 单手全桌动作数范围 |
|---|---:|---:|---:|
| rc3 PPO训练 | 6406 | 6406 | 48–392 |
| baseline评估 | 4096 | 1024，每墙4次 | 68–396 |
| 每份候选评估 | 4096 | 1024，每墙4次 | 其中最短56、最长396 |

动作数含摸打响应中的PASS，不是独立监督题数量。训练记录平均318.59次全桌动作/手。训练与这五份评估的起始墙交集为0；训练内无重复。另从6个牌谱文件各取前8手，共48手，按原规则重新逐步执行动作并重建结算，全部通过。详细结果为`verification/data_protocol/real-rc3-hand-audit.json`。

这是对这份rc3归档的结论，不是对所有历史权重经历过的全部牌墙的证明。旧rc1教师预训练牌墙只在内存，没有完整落盘；缺失的历史不能伪造。

## 4. 旧rc4确实存在的数据协议缺口

原`RefinementConfig`和`train_refinement.py`默认训练种子是20261003；启动时重新建立环境，桌种子从该根种子固定推导。旧rc3/rc4以同种子同桌数重新运行时，会重播相同的环境起始随机流。单个run内部RNG会前进，所以不是每批只重刷同一局。模型动作改变后轨迹不一定一致，但这不消除跨版本数据复用。

旧开发集默认evaluation_seed=95000731，在多次候选、多个版本重复使用。固定开发牌墙便于配对比较，本身合理；它不参与PPO梯度，但多次人工调参/挑候选可能使开发集结论过于乐观。旧独立验证入口虽然存在，不能把“有这个命令”等价成“真实模型已经通过独立验证”。

过去日志不足以证明模型已经过拟合，也不足以证明其泛化良好。应检验，而不是凭训练均分或单个固定开发集下结论。

## 5. rc4.1修复后的数据流

新run默认由系统熵生成根种子并持久化。训练各桌与开发评估使用按用途派生的独立随机流；每次启动默认不同，显式`--seed`仅用于可复现研究。一个run的开发墙固定，多个候选、四座位复用属于有意配对。

训练终局在进入PPO前登记实际有序牌种墙。登记库`.wall-exposures.sqlite3`位于输出根目录，保留跨run暴露。登记也包括结算时预发下一局和独立马牌墙，同一预发局后续实际打牌不误报。跨用途、跨run或意外重复将报错，不偷偷丢掉样本后继续、也不把复制编号当新墙。

启动前只读导入所选候选源run及可达祖先的已记录训练/评估墙。内容哈希缓存避免反复扫描。历史不可达、旧教师只存内存、旧评估只有摘要时，`missing_history`明确列出并把`historical_coverage`标为partial。只能承诺排除已知暴露，不能宣称未知历史也完全隔离。

最终验证默认再生成新种子，先冻结一个候选，再用新墙同时评估起点与候选。同一轮验证两模型的墙必须相同；跨轮不能将已登记验证墙当新数据使用。独立验证仍是只读模型的单独命令，不更新网络。

完整同墙去重不禁止相似起手、常见牌型或共享前缀，也不构成数学意义的所有样本统计独立。有限测试仅检验特定规则、对手和牌墙分布下的泛化；多个训练种子、其他对手和跨局会话仍需另行验证。

## 6. 执行边界

弃用旧rc4 ZIP作为本轮入口；使用rc4.1重新prepare，因为运行计划绑定源码哈希。编译/性能基准仍有意使用固定输入重复测试，不执行PPO、不选策略模型，不能计入新训练样本。

新训练不要填写固定`--seed`或`--evaluation-seed`。观察`data-integrity.json`的真实种子、独立开发墙数、完整训练局数、历史覆盖范围和已知暴露登记。开发PASS也不能把`generalization_verified`或`long_training_allowed`改成true。

保持原有分阶段执行：准备→受控训练→冻结候选→新墙独立验证。下载新包并不等于批准立即开长训。

## 方法背景（不替代源码证据）

Cobbe等，ICML2019《Quantifying Generalization in Reinforcement Learning》指出同环境训练和测试难以说明泛化，使用程序生成的分离训练/测试集合进行检验。来源：https://proceedings.mlr.press/v97/cobbe19a.html

PyTorch官方Reproducibility说明可控随机种子有助于复现，但不保证不同版本/平台/设备完全重现。来源：https://docs.pytorch.org/docs/2.13/notes/randomness.html

以上是外部方法依据；本项目是否完整对局、重复多少，以本次源码核对与真实牌谱审计为准。
